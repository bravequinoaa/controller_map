# M2 plan: Binding, output, and live apply

Saved plan, not yet executed. Written for whoever (human or a future Claude
Code session) picks up M2 next — read this in full before writing any code
for this milestone, alongside `CLAUDE.md`, `architecture.md`, `design.md`,
and `__Design Documentation/critique/M0.md` + `pre-M1.md`.

## Context

M0 (core skeleton) and M1 (real device via Windows Raw Input, plus a post-M1
critique fix making the Raw Input listener a ref-counted singleton) are done
and committed (branch `M1`, commit `61da263` plus the uncommitted pre-M1 fix
described in `critique/pre-M1.md`). M2 is the next milestone in `CLAUDE.md`'s
build order: FR-4 (binding), FR-6 (live apply), FR-7 (persistence).
Acceptance bar, verbatim from `CLAUDE.md`: pressing pedal button 1 sends a
bound keystroke, and the mapping survives a restart.

This plan was produced interactively with the project owner before any M2
code was written; three scope questions were asked and answered, recorded
below as decisions rather than open questions.

## Decisions

1. **Fire timing: DOWN only, for now — but keep it a clean extension point.**
   Bound actions fire once, on the button-DOWN edge. UP is still tracked
   (needed for chord timing later, M7) but never dispatches actions today.
   This was a deliberate scope call, not an oversight: `Trigger` (per
   `architecture.md`'s UML) carries no down/up notion at all — it represents
   "this set of buttons was actuated" — so edge filtering is correctly an
   `Engine`-level concern, not a `Trigger`-level one. Firing on both edges
   was explicitly *not* ruled out for later, though, and the design below
   isolates the DOWN-only check behind one small, named piece of `Engine`
   state (`_fire_on_states`, see the Engine section) rather than an inline
   condition buried in the worker loop, specifically so that widening it —
   or, more likely, adding a per-`Binding` `fire_on` field so individual
   bindings can opt into DOWN/UP/BOTH independently — is an additive change
   to `Engine`/the data model, not a restructure of the dispatch loop.
2. **`ProfileResolver` deferred to M5.** M2's `Engine` picks
   `Config.default_profile_id` directly. `core/profiles.py` gets built when
   M5 (profile switching) actually needs `resolve()`; M6 (app-detection) is
   what exercises its match-rule logic for real. Building it now would mean
   a pure function nothing calls with real data yet.
3. **`Engine`'s API is minimal for M2:** `start()` / `stop()` / `reload()`
   only. `set_recording`, learn-button, and device-listing methods arrive
   with M3/M4 when there's an actual caller and a test for them, not stubbed
   ahead of need.

## What gets built

### 1. `core/ports.py` — one small, justified addition
Add a non-abstract `InputDevice.load_signatures(self, signatures: dict[str, int]) -> None: pass`
(default no-op), following the same optional-capability-hook pattern already
used for `grab()`/`ungrab()`. This lets `Engine` restore learned buttons on
startup through the port, without knowing about `HidPedal` specifically.
`HidPedal` already implements a method with this exact name/signature
(`devices/hid_pedal.py`), so this just promotes it to the port contract.

### 2. `core/actions.py` (new file)
`ActionExecutor.execute(actions: list[Action], sink: OutputSink) -> None`.
Not named in `CLAUDE.md`'s repo-layout table (only `engine.py` is), but
`architecture.md`'s UML draws it as its own class (`Engine o-- ActionExecutor`),
so it gets its own file rather than living inside `engine.py` or `events.py` —
mirrors how `chords.py`/`profiles.py`/`recorder.py` each get their own file
for one core class.

- Dispatches on `Action.type`: `KEY` -> `sink.send_key(params["keys"])`,
  `MOUSE` -> `sink.send_mouse(params["button"])`, `TEXT` -> `sink.type_text(params["text"])`,
  `LAUNCH` -> `sink.launch(params["target"])`, `DELAY` -> `time.sleep(params.get("seconds", 0))`.
- Each action wrapped in its own `try`/`except Exception`, logged via
  `logging.exception` and the loop continues to the next action — same
  fail-soft shape already used for subscriber fan-out in
  `devices/raw_input.py`, and required by NFR-4 ("a failed action logs and
  continues").

### 3. `core/engine.py` (new)
`Engine.__init__(self, store: ProfileStore, devices: list[InputDevice], sink: OutputSink)`.

- `start()`:
  - `self._config = self._store.load()`
  - For each device: look up its `DeviceInfo` in `self._config.devices` by
    `device_id`; if found, call `device.load_signatures({sig.signature: sig.button_id for sig in info.buttons})`.
  - Create `self._queue: queue.Queue[ButtonEvent | object]`, start each
    device with `device.start(self._queue.put)` — this *is* the queue
    boundary the M1 critique's Finding 2 flagged as "M2 day-1 work":
    `queue.put` is the only thing ever called directly from a device's own
    thread, satisfying the fast/non-blocking contract already documented on
    `InputDevice.start` and `RawInputSource`.
  - Spawn `self._worker` (daemon thread) running `_run()`.
- `_fire_on_states: frozenset[ButtonState]` — set once in `__init__` to
  `frozenset({ButtonState.DOWN})`. `_run()` checks membership here rather
  than comparing to `ButtonState.DOWN` inline; this is the clean extension
  point decision 1 above describes. Do not inline this check when writing
  `_run()` even though it looks like a one-line simplification — the whole
  point is that it isn't inlined.
- `_run()`: blocking `self._queue.get()` loop.
  - A sentinel object (`_STOP`) put by `stop()` breaks the loop cleanly.
  - Skip any event whose `state` is not in `self._fire_on_states`.
  - Build `Trigger(TriggerKind.BUTTON, event.device_id, frozenset({event.button_id}))`.
  - Resolve the active profile directly: `next(p for p in self._config.profiles if p.id == self._config.default_profile_id)`.
  - Linear-scan the profile's bindings for a matching `trigger` (fine at
    this scale — the M1 critique already called out linear scans here as
    correctly sized, no indexing needed).
  - Found -> `ActionExecutor.execute(binding.actions, self._sink)`.
    Not found -> log (info/debug) and continue: this is the "unknown
    binding" fail-soft case NFR-4 names.
  - The whole per-event body wrapped in `try`/`except Exception` + log, so
    one bad event can't kill the worker thread.
  - `self._config` access guarded by a `threading.Lock` (read in `_run`,
    swapped in `start`/`reload`) — explicit per `architecture.md`'s "Config
    is guarded by a lock and swapped atomically on reload," even though a
    bare reference swap would be safe under the GIL; being explicit matches
    the documented model instead of relying on that implicitly.
- `stop()`: `device.stop()` for each device, push `_STOP`, join the worker
  thread.
- `reload()`: re-`self._store.load()` under the same lock.

### 4. `platform/output.py` (new)
`PynputOutputSink(OutputSink)` using `pynput.keyboard.Controller` /
`pynput.mouse.Controller`.

- `send_key(keys)`: a small name->key table (`ctrl`, `shift`, `alt`, `cmd`,
  `enter`, `esc`, `tab`, arrows, `f1`-`f12`, ...) falling back to
  `KeyCode.from_char` for single printable characters; press all then
  release in reverse order. The name-resolution piece is factored into a
  pure `_resolve_key(name: str)` function so it's unit-testable without
  mocking `pynput.keyboard.Controller` itself.
- `send_mouse(button)`: map `left`/`right`/`middle`/`x1`/`x2` to
  `pynput.mouse.Button`, click once.
- `type_text(text)`: `keyboard.Controller().type(text)`.
- `launch(target)`: `os.startfile(target)` (Windows-only, matches this
  file's existing Windows scope; avoids `shell=True` injection risk
  entirely since it never goes through a shell). `design.md`'s schema
  example is a bare exe name (`"notepad.exe"`), not an argv string, so this
  covers FR-4 as specified; extending to argument-carrying launch strings is
  a later refinement if actually needed.

### 5. `persistence/store.py` (new)
`JsonProfileStore(ProfileStore)`, constructed with a `Path`.

- `load()`: file missing -> return a fresh default `Config` (version 1,
  `default_profile_id="default"`, one empty `Profile(id="default", name="Default")`,
  no devices) so callers never need a separate "first run" branch. File
  present -> parse JSON, dispatch on `data["version"]`; only version 1 exists
  today, so the dispatcher is a single branch plus a clear `ValueError` for
  anything else, structured so a real migration slots in later without
  reshaping the function.
- `save(cfg)`: hand-written (de)serialization (not `dataclasses.asdict`,
  since `frozenset` and `Enum` fields need explicit conversion) to a
  JSON-safe dict matching `design.md`'s schema, written atomically (temp
  file + `os.replace`) so a crash mid-write can't corrupt the config.
  Serialization logic lives entirely here, not on the `core` dataclasses —
  keeps `core` JSON-oblivious, matches this file's stated responsibility
  ("versioned load/save + migrate").
- **Coverage gap, called out rather than papered over:** `CLAUDE.md`'s
  Testing section asks for "persistence round-trip plus a version
  migration." There is no prior schema version to migrate *from* yet
  (version 1 is the only one that has ever existed), so writing a migration
  test now means inventing a fake historical format purely to exercise a
  mechanism nothing has used yet — that's the kind of speculative
  future-proofing the project explicitly avoids elsewhere. What M2 tests
  instead: the round-trip itself, and that an unrecognized `version` fails
  clearly rather than silently. A real migration test lands whenever a
  version 2 actually exists.

### 6. `tests/fakes.py` — add `FakeOutputSink`
Records `(method, args)` calls in a list, as `CLAUDE.md`'s Testing section
already specifies. Small, mirrors `FakeInputDevice`'s existing style.

### 7. Tests
- `tests/test_actions.py`: `ActionExecutor` dispatches each `ActionType`
  correctly via `FakeOutputSink`; one bad action logs and doesn't stop the
  rest of the list from running.
- `tests/test_engine.py`: `FakeInputDevice` + `FakeOutputSink` + a
  `JsonProfileStore` pointed at `tmp_path` (real store, not a fake, since
  there's nothing hard to fake about it). Covers: DOWN on a bound trigger
  fires the right sink calls; UP alone fires nothing; an unbound trigger
  doesn't raise; two devices route independently; `stop()` joins cleanly.
  Because `Engine` processes events on its own worker thread, assertions
  after `emit()` poll `fake_sink`'s recorded calls with a short bounded
  timeout rather than sleeping a fixed amount or reaching into `Engine`'s
  internals — deterministic enough for an in-process, no-I/O test.
- `tests/test_persistence.py`: round-trip a `Config` with nested
  `Profile`/`Binding`/`Trigger`/`Action`/`DeviceInfo`/`ButtonSignature`
  (including `frozenset` and enum fields) through `save`/`load`; missing
  file returns the bootstrapped default; unsupported `version` raises
  clearly.
- `tests/test_output.py`: unit-test `_resolve_key` name resolution directly
  (no mocking needed). `PynputOutputSink` itself isn't unit-tested beyond
  that — same category as `devices/raw_input.py`'s real Win32 calls, which
  are only exercised at their boundary (`test_raw_input.py` mocks specific
  `user32` entry points), not end-to-end.

### 8. `requirements.txt`
Add `pynput` (pinned to whatever version installs cleanly).

### 9. Demo script: `scratch_apply.py`
Mirrors the `scratch_learn_and_print.py` pattern from M1, real hardware, no
GUI, proves the acceptance bar directly:

1. Enumerate the pedal, build `HidPedal`, point `JsonProfileStore` at a
   config file in the repo (e.g. `./config.json`, gitignored).
2. `store.load()`. If the pedal has no `DeviceInfo` in it yet: run M1's
   `learn_buttons()`, build a `Config` with that device's `ButtonSignature`s
   and a default profile binding button 1 -> a clearly-observable action
   (e.g. `type_text` a marker string, easy to see land in a text editor),
   `store.save(cfg)`.
3. Build `PynputOutputSink`, construct `Engine(store, [pedal], sink)`,
   `start()`.
4. Print instructions, wait for the user to press button 1, observe the
   typed text land in whatever has focus.
5. `stop()`.
6. Running the script a **second time** skips step 2 (config already has the
   device's signatures and the binding) and applies immediately — this is
   the "survives a restart" half of the acceptance bar.

## Verification

- `python -m pytest -v` — all new tests plus the existing 9 stay green.
- Run `scratch_apply.py` twice against the real pedal (first run does the
  learn+persist step, second run loads straight from disk); confirm button 1
  produces the bound output both times, and that quitting between runs
  (process exit) doesn't lose the mapping.
- Recheck the dependency rule after adding files: `core/actions.py` and
  `core/engine.py` must still only import from `core` and the stdlib
  (`grep -n "^import\|^from" core/*.py`, same check used after M1).

## Not in this plan (explicitly deferred, not forgotten)

- `core/profiles.py` / `ProfileResolver` — M5.
- `core/chords.py` / `ChordResolver` — M7. M2's `Trigger` construction is a
  direct single-button passthrough with no chord window.
- `core/recorder.py` — M3.
- Engine's `set_recording`/learn-button/device-listing API — M3/M4.
- Firing bound actions on the UP edge (or per-binding edge selection) — not
  built now, but decision 1 above records why the design keeps it a cheap
  add later rather than a rewrite.
- Two small pieces of repo hygiene noticed while syncing with the critique
  docs, unrelated to M2 itself, flagged for a separate decision rather than
  folded in here: `CLAUDE.md` still references `Design Documentation/...`
  after the folder was renamed to `__Design Documentation`, and
  `__pycache__`/`.pyc` files are currently tracked in git.
