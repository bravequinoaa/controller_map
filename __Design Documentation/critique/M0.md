# M1 Critique — Lead Engineer Review

Reviewed at end of Phase 2 (M1: real device + button learning), before M2
(binding/output/live apply) begins. Scope: `core/events.py`, `core/ports.py`,
`devices/base.py`, `devices/hid_pedal.py`, `devices/raw_input.py`, and their
tests. Read `Design Documentation/architecture.md` and `design.md` alongside
this — findings below are checked against NFR-1, NFR-6, and the concurrency
model those docs already commit to.

Purpose of this doc: flag what should be resolved *before* `engine.py` and
multi-device support get built on top of the current shape, since both findings
below get materially more expensive to fix once callers depend on today's
API. This is not a blocker list for M1 itself — M1's stated acceptance
criteria (distinct, stable `ButtonEvent`s after a learn pass) are met. It's
input for deciding what M2 needs to carry forward differently.

## What's solid (keep doing this)

- Dependency rule is respected: no `hid`, `pynput`, or `win32*`/`ctypes` in
  `core/`. `core/events.py` and `core/ports.py` are pure.
- The Raw Input workaround (`devices/raw_input.py`) is well-justified in its
  own docstrings — it explains why hidapi reads fail on this device and why
  the fallback doesn't need to leak into `core`. Keep that standard of
  in-file rationale for future OS-specific workarounds.
- `normalize_hid_path` correctly reconciles the two device-interface-class
  GUIDs hidapi and Raw Input expose for the same physical interface, and is
  tested against both a real collapsing case and a real distinguishing case
  (`tests/test_base.py`).
- Edge-only `ButtonEvent` emission (`devices/hid_pedal.py:84-87`) correctly
  filters Raw Input's auto-repeat, and is tested (`test_hid_pedal.py`).
- Test doubles (`FakeInputDevice`, `FakeRawInputSource`) match the ports
  they stand in for and don't leak implementation details.

## Finding 1 (fix before M2): `RawInputSource` cannot have two live instances in one process

**Where:** `devices/raw_input.py:280` (hardcoded window class name
`"PedalControllerRawInputWindow"`), `devices/raw_input.py:282-284` (unchecked
`RegisterClassW` return), `devices/raw_input.py:295` (unchecked
`RegisterRawInputDevices` return), `devices/hid_pedal.py:38` (`HidPedal`
creates its own `RawInputSource` by default).

**Problem:** Each `HidPedal` owns a private `RawInputSource`, which
registers a process-global Win32 window class and a process-global
`RegisterRawInputDevices` subscription for the generic keyboard/mouse usage
pages. Both are process-wide resources in the Win32 API, not per-instance
ones. If a second `HidPedal` is started while the first is still running:

- `RegisterClassW` fails (`ERROR_CLASS_ALREADY_EXISTS`) because the class
  name is already registered. The code doesn't check the return value —
  `_run()` just calls `self._ready.set()` and returns (`raw_input.py:283`),
  so `start()` reports success even though no window exists and no `WM_INPUT`
  will ever arrive on that thread. This fails silently; nothing raises,
  nothing logs.
- `RegisterRawInputDevices` for a given (usage page, usage) pair is also
  process-global — the second registration either fails or reassigns
  delivery target away from the first listener.

**Why it matters:** `core/events.py:69` (`logical_device_id`) already
reserves an `#index` suffix specifically for "several identical devices...
present" (NFR-6), and `architecture.md`'s concurrency section describes a
device-read thread feeding a queue in terms that assume one physical input
source is being multiplexed, not one OS-level listener spun up per device.
The current code is structurally single-device: it works today only because
nothing has instantiated two `HidPedal`s yet. This will surface as a
hard-to-debug silent failure ("second pedal just doesn't do anything") the
first time multi-device support is exercised, and by then `Engine` and
possibly the GUI will hold references shaped around today's per-`HidPedal`
listener assumption, making the fix more invasive.

**Direction for the team to evaluate (not prescriptive):** the natural shape
is a single process-wide `RawInputSource` (singleton or owned by whatever
composition root wires devices) that dispatches by `device_path` to whichever
`HidPedal` instances are listening, rather than each `HidPedal` owning one.
Worth deciding now whether that shared listener lives in `devices/base.py`,
as a module-level singleton in `raw_input.py`, or is injected by `app.py` /
`Engine` at startup — pick whichever keeps `core` untouched and keeps the
existing `raw_input=` constructor injection point for tests. Also decide
whether to surface the currently-silent registration failures as exceptions
or logged errors per NFR-4 ("a bad binding or failed action logs and
continues; it never takes down the engine") — a failed *listener*
registration is arguably a harder failure than that NFR covers and may
warrant surfacing to the GUI rather than swallowing.

## Finding 2 (decide before M2 wiring): no queue boundary yet between the OS thread and event consumers

**Where:** `devices/raw_input.py:333-336` (`_handle_input` invokes
`on_event` directly), `devices/hid_pedal.py:89-97` (`_on_raw_event` invokes
the caller's `on_event` directly). Both calls happen synchronously on the
thread running `GetMessageW`/`DispatchMessageW`.

**Problem:** This is a direct call chain from the Win32 message pump all the
way to whatever `on_event` callback `Engine` eventually supplies. Fine today
because nothing consumes events yet. But `architecture.md`'s concurrency
section specifies: device thread blocks and pushes to a queue; a separate
engine worker thread drains it, runs chord resolution, and dispatches
actions. If M2 wires `Engine`'s `on_event` straight into this callback chain
instead of through a queue, any slow consumer downstream (chord window wait
in M7, a `LAUNCH` action spawning a process, `pynput` key synthesis blocking
on the OS) stalls delivery of `WM_INPUT` on that thread — risk to the ~50ms
NFR-1 budget and to not dropping presses under load.

**Direction for the team to evaluate:** confirm `Engine`'s `start()` puts a
`queue.Queue` between `InputDevice.start(on_event)` and the worker thread
that runs chord resolution + dispatch, per the architecture doc, rather than
treating `on_event` as a place to hang consumer logic directly. This is
mostly a "don't build it the other way" flag for M2, not new design work —
the architecture doc already specifies the right shape.

## Minor, cheap to fix now

- `RawInputEvent.timestamp` uses `time.time()` (`raw_input.py:319`), not
  `time.monotonic()`. Chord-window timing (M7, NFR-1) should be immune to
  wall-clock adjustments (NTP sync, manual clock change mid-hold). Cheap to
  switch at the source now versus threading a monotonic-vs-wall-clock
  conversion through `ChordResolver` later. `ButtonEvent.timestamp`
  downstream should follow whichever the team picks here.

## Explicitly not a concern — don't spend M2 time on these

- Single-file JSON persistence, linear-scan profile/binding lookup, and the
  signature dict in `HidPedal` are all correctly sized for a single-user
  desktop tool with a handful of profiles and bindings. Adding indexing or a
  database here would be over-engineering; no action needed.
